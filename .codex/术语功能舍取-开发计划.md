# 术语功能舍取开发计划

Created: 2026-06-11
Source plan: `.codex/术语功能舍取-autoplan.md`

## 目标

按 Approach B 落地：保留 `BusinessTerm` 模型、terms API、运行时术语归一化、冲突澄清和语义验证观测能力；前端将“业务术语”从普通一级主路径降级为“语义词典 / 别名与口径”的高级治理能力，并把候选别名处理嵌入分析蓝图、指标、维度等主资产流程。

本计划只做前端信息架构和交互收敛，不删除后端模型和运行时节点。

## 开发原则

- 保留运行时闭环：`term_normalize_node`、术语冲突澄清、知识解释和语义验证报告不能退化。
- 降低主路径噪音：普通用户优先看到数据表、字段、指标、维度、分析蓝图、语义验证。
- 保留高级治理：数据治理人员仍能进入语义词典，做搜索、编辑、删除、冲突检测和关联资产查看。
- 不复制存储：蓝图、指标、维度中出现的候选别名最终仍调用现有 terms API，不新增一套 term 数据。
- 候选不阻塞：建议别名、候选术语、冲突提示都不能阻塞蓝图保存和发布，除非用户明确选择处理。

## 阶段安排

### Phase 0：基线确认

目标：确认当前页面和运行时闭环可回归，避免信息架构改造时误伤。

任务：

- 记录当前数据集能力页 `capabilityTabs`、`renderTermsPanel`、语义验证报告和术语弹窗入口。
- 记录蓝图向导第 2 步、测试发布流程、低置信字段提示区域。
- 确认 `datalogue-web/src/api/client.js` 已有 `listBusinessTerms`、`createBusinessTerm`、`updateBusinessTerm`、`deleteBusinessTerm`、`linkBusinessTermAssets`、`discoverBusinessTerms`、`checkBusinessTermConflicts`。

产出：

- 不改代码，只作为实现前检查。

验收：

- 能明确哪些 UI 迁移、哪些 UI 保留、哪些 API 复用。

### Phase 1：数据集能力页信息架构收敛

目标：业务术语不再作为普通一级主 Tab；迁入高级治理入口。

涉及文件：

- `datalogue-web/src/components/datasets.jsx`

任务：

- 将 `capabilityTabs` 拆成主路径和高级治理两组。
- 主路径保留：数据表、字段标注、指标、维度、分析蓝图、语义验证。
- 将 `terms` 从普通一级 Tab 移入 `高级治理`，命名为 `语义词典` 或 `别名与口径`。
- `permissions`、`versions` 暂时可一起放入高级治理，避免主路径 Tab 继续膨胀。
- 保留 `renderTermsPanel`，但更新标题、说明和空状态文案：
  - 标题：`语义词典`
  - 定位：`治理跨资产别名、冲突和解释口径`
  - 空状态：`当前无词条，不影响问数；可从蓝图、指标、维度中沉淀别名`
- 将术语统计卡从主路径感知中降级，只在高级治理页面内部展示。

验收：

- 默认进入数据集能力页时，看不到“业务术语”作为普通一级主 Tab。
- 用户仍能通过高级治理进入语义词典。
- 原术语列表、详情、搜索、筛选、新建、编辑、删除、冲突检测能力仍可用。
- 语义验证报告仍展示术语命中和蓝图命中。

### Phase 2：蓝图向导内嵌“建议别名与口径”

目标：用户创建蓝图时顺手处理候选别名，不再单独进入术语工作台。

涉及文件：

- `datalogue-web/src/components/analysis-blueprints.jsx`
- `datalogue-web/src/api/client.js`

任务：

- 在蓝图向导第 2 步“确认 AI 生成的蓝图草稿”增加紧凑区域：`建议别名与口径`。
- 候选来源先使用蓝图草稿已有信息：
  - `name`
  - `trigger_keywords`
  - `trigger_examples`
  - `parameters`
  - `output_schema`
  - `businessRules`
- 第一版不强制新增后端候选接口；优先复用现有 terms API：
  - 接受候选：调用 `createBusinessTerm`
  - 若需要关联蓝图或资产：调用 `linkBusinessTermAssets`
  - 重复名 409：转为“复用已有词条”提示
- 每个候选行提供：
  - 候选名称
  - 来源字段
  - 建议类型
  - 操作：接受、忽略、复用已有
- 候选生成失败、无候选、重复候选都不能阻塞蓝图下一步、保存草稿或发布。

验收：

- 蓝图 AI 草稿生成后，可看到或明确看不到候选别名。
- 接受候选后，术语可在高级治理的语义词典中看到。
- 忽略候选后，蓝图仍可继续保存和发布。
- 重复候选不重复创建 term。

### Phase 3：交互状态和错误处理补齐

目标：让术语降级后的关键状态可解释、可恢复。

涉及文件：

- `datalogue-web/src/components/datasets.jsx`
- `datalogue-web/src/components/analysis-blueprints.jsx`

任务：

- 语义词典列表状态：
  - loading：列表骨架或按钮 loading
  - empty：说明无词条不影响问数
  - error：显示重试入口和错误原因
  - partial：关联资产加载失败时保留词条列表
- 蓝图候选别名状态：
  - loading：`正在检查别名和口径`
  - empty：`未发现需要沉淀的别名`
  - error：`暂未生成建议，不影响蓝图保存`
  - success：行项显示 `已沉淀`
  - conflict：409 显示 `已存在，建议复用`
- 冲突检测状态：
  - loading：禁用重复点击
  - empty：`当前未发现冲突`
  - error：保留列表并提示重试
  - partial：显示跳过项

验收：

- 断开 terms API 或返回错误时，主路径可继续使用。
- 409 重复名有明确文案，不出现只有 alert 的粗糙失败。
- 多个候选批量处理时，失败项不会吞掉成功项。

### Phase 4：语义验证与聊天澄清回归

目标：确认前端降级术语入口后，运行时价值仍然可见。

涉及文件：

- `datalogue-web/src/components/datasets.jsx`
- `datalogue-web/src/assistant/MyMessage.jsx`
- 后端相关测试文件按需回归，不主动改动

任务：

- 语义验证报告保留：
  - 术语命中
  - 蓝图命中
  - route
  - SQL
  - 失败原因
- 调整术语命中视觉层级：作为验证证据，不作为主操作 CTA。
- 确认聊天术语澄清卡片仍可选择候选并继续原问题。
- 候选项过多时，至少不破坏布局；后续再考虑搜索或折叠。

验收：

- 普通问数命中术语别名时，语义验证可看到术语命中。
- 术语冲突时，聊天侧仍展示澄清卡片。
- 用户选择术语后，原问题继续执行。

### Phase 5：响应式与可访问性收尾

目标：避免高级治理迁移后在窄屏和键盘操作上退化。

涉及文件：

- `datalogue-web/src/components/datasets.jsx`
- `datalogue-web/src/components/analysis-blueprints.jsx`
- `datalogue-web/src/assistant/MyMessage.jsx`

任务：

- 高级治理入口在桌面、平板、移动端都可见。
- 语义词典在移动端先显示搜索和列表，点词条进入详情或抽屉。
- 蓝图候选别名区域在窄屏默认折叠，只显示候选数量和冲突状态。
- 所有接受、忽略、复用操作使用 `<button>`。
- 冲突和失败状态必须有文本，不只靠颜色。
- 搜索框补 `aria-label` 或可见 label。
- 弹窗或抽屉关闭后，焦点回到触发按钮。

验收：

- 键盘 Tab 可以访问候选操作。
- 移动端没有 10 个 Tab 挤满首屏的问题。
- 按钮触摸目标不小于 44px。



手工验收：

- 高级治理入口可进入语义词典。

## 风险与回滚

| 风险 | 影响 | 规避 | 回滚 |
|---|---|---|---|
| 高级治理入口太隐蔽 | 数据治理人员找不到语义词典 | 入口命名清晰，放在能力页固定位置 | 临时把语义词典恢复为二级明显入口 |
| 蓝图候选别名引入保存阻塞 | 用户无法顺利发布蓝图 | 候选区域永远非必填，失败只提示 | 关闭候选区域，仅保留蓝图原流程 |
| 409 重复处理不清晰 | 用户重复创建或困惑 | 明确显示复用已有词条 | 回退为仅提示重复，不自动创建 |
| terms lazy-load 改动影响页面 | 数据集页初始化异常 | 第一阶段不改后端和加载策略，必要时再优化 | 恢复当前并行加载 terms |
| 运行时术语澄清退化 | 问数歧义无法恢复 | 不改 `term_normalize_node` 和 `TermClarificationCard` 主逻辑 | 回退聊天卡片改动 |

## 明确不做

- 不删除 `BusinessTerm` 相关模型和数据库表。
- 不删除 `/api/dataset/{ds_id}/terms...` API。
- 不删除 `term_normalize_node`。
- 不把术语全部迁移为指标或维度 synonyms。
- 不在本阶段实现完整知识库检索。
- 不在本阶段做 terms top-K 召回优化。

## 完成定义

- 用户主路径以分析蓝图、指标、维度和语义验证为中心。
- 术语作为语义词典存在于高级治理中，不再和分析蓝图并列抢主路径。
- 蓝图创建过程可以顺手沉淀别名和口径，但不强制。
- 问数运行时的术语归一、冲突澄清、知识解释和语义验证观测不退化。
- 前端 lint/build 通过，后端术语和聊天相关测试通过。
