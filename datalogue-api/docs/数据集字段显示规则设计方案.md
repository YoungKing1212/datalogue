# 数据集字段显示规则（Display Rules）设计方案

> 状态：待评审
> 日期：2026-06-03
> 范围：`datalogue-api/app/models/` + `app/schemas/` + `app/utils/prompt.py` + `app/graph/` + `datalogue-web/src/components/datasets.jsx`

---

## 一、背景与目标

### 1.1 当前痛点

数据集级 LLM 约束（`prompt_instructions`）已经能解决单条规则问题，但**当"编码→名称"映射变多时，自由文本撑不住**：

| 场景 | 当前做法 | 痛点 |
|---|---|---|
| 1 个字段（如 deptcode） | 在 `prompt_instructions` 写 1 条规则 | 可行，已验证 |
| 5-10 个字段 | 写多条规则 + 通用模式 + 示例 | prompt 越来越长，LLM 开始"挑"着执行 |
| 20+ 个字段 | 自由文本完全不可控 | LLM 不会 100% 照做；规则维护成本高 |

**用户的实际诉求**：
> "如果有多种场景，不止 deptcode，可能这种关联关系有好多，这种怎么干啊，不可能每条这么写吧"

需要一个**结构化、可配置、可观测**的字段显示规则管理机制。

### 1.2 设计目标

1. **支持多条规则**：数据集级别维护一组"DDL 字段 → 可读展示"的映射
2. **新规则添加不需改代码**：通过 UI 配置即可生效
3. **可观测**：prompt 中渲染出来的规则表对运营/调试透明
4. **兼容现有 `prompt_instructions`**：自由文本继续作为兜底（边界场景、临时规则）

### 1.3 非目标（明确不做）

- ❌ 自动从 `source_column` 标注推导规则（标注数据太脏，机器推导不准）
- ❌ 跨数据集规则共享（每个数据集有独立的语义，复用反而混乱）
- ❌ 规则冲突检测（两个规则引用同一个 source_column）
- ❌ 字段级 UI 编辑器（先做 JSON 文本框，验证机制可用后再升级）

## 二、方案对比

### 思路 A：自由文本 + Few-shot 示例

**数据载体**：复用现有 `prompt_instructions` Text 字段  
**约定格式**：通用规则 + 已知映射示例

示例文案：
```
【字段显示规则】
任何 *_code / *_id / 包含"编码"字样的字段，SQL 必须 LEFT JOIN 对应维表，
把维表里可读字段（_name / _label / 描述）一并 SELECT 出来；
报告展示时只用可读字段，不用编码。

已知映射（参考）：
- plan_task_daily_record.deptcode → sys_dept.dept_name
- 订单状态 status → sys_dict.dict_label （如果有字典表）
```

| 维度 | 评价 |
|---|---|
| 改动量 | **零**（文案用户自己写） |
| 规则数量 | 5-10 条以内勉强可控 |
| 可靠性 | LLM "挑"着做，**不一致** |
| 可观测性 | 黑盒——只能从最终 SQL/报告反推 |
| UI 成本 | 0 |

**适用场景**：早期、规则少、用户愿意手维护。

### 思路 B：结构化 Display Rules（推荐）

**数据载体**：新增 `display_rules` JSON 字段  
**后端渲染**：在 `build_schema_prompt` 里把 JSON 渲染成"映射表"塞进 prompt

数据模型（每条规则）：
```json
{
  "source_table": "plan_task_daily_record",
  "source_column": "deptcode",
  "lookup_table": "sys_dept",
  "lookup_key": "dept_id",
  "display_column": "dept_name",
  "description": "部门编码 → 部门名称"
}
```

Prompt 渲染产物（自动拼到 LLM 输入）：
```
【字段显示规则（SQL 阶段必须遵循）】
| source_column | lookup_table | display_column | 说明 |
|----------------|--------------|----------------|------|
| plan_task_daily_record.deptcode | sys_dept (key=dept_id) | dept_name | 部门编码 → 部门名称 |

统一要求：
- SQL 涉及 source_column 时必须 LEFT JOIN lookup_table，按 lookup_key 关联
- SELECT 一并带上 display_column AS <原列名>_name
- 报告阶段：展示时用 display_column 替代 source_column
```

| 维度 | 评价 |
|---|---|
| 改动量 | **中等**：1 字段 + 1 迁移 + 1 schema + 1 prompt 渲染 + 1 UI |
| 规则数量 | **无上限** |
| 可靠性 | 结构化输入 → LLM 输出**稳定** |
| 可观测性 | 完全透明——prompt 里的表格就是规则本身 |
| UI 成本 | 先做 JSON 文本框（10 行代码） |

**适用场景**：长期方案，规则会持续增长。

## 三、推荐方案：思路 B（最小可用版）

### 3.1 实施分阶段

#### Phase 1：后端模型 + Schema + 迁移（必须）

**新文件**：`datalogue-api/alembic/versions/<hash>_add_dataset_display_rules.py`

照搬 `e47d3004182b` 模板：
```python
def upgrade():
    op.add_column('semantic_dataset', sa.Column('display_rules', sa.JSON(), nullable=True))

def downgrade():
    op.drop_column('semantic_dataset', 'display_rules')
```

**模型** `app/models/dataset.py`：
```python
display_rules = Column(JSON, default=list)  # 列表 or None
```

**Pydantic 子模型** `app/schemas/dataset.py`：
```python
class DisplayRuleItem(BaseModel):
    source_table: str
    source_column: str
    lookup_table: str
    lookup_key: str
    display_column: str
    description: Optional[str] = None
```

**DatasetCreate / DatasetUpdate / DatasetOut**：
```python
display_rules: List[DisplayRuleItem] = []  # Create
display_rules: Optional[List[DisplayRuleItem]] = None  # Update
display_rules: List[DisplayRuleItem] = []  # Out
```

#### Phase 2：Prompt 渲染（必须）

**新建工具** `app/utils/display_rules.py`：

```python
def render_display_rules_prompt(rules: list[dict] | None) -> str:
    """把 display_rules JSON 渲染成 LLM 可读的规则表段。
    空列表/None → 返回空串（不注入）。
    """
    if not rules:
        return ""
    lines = ["【字段显示规则（SQL 阶段必须遵循）】"]
    lines.append("| source_column | lookup_table | display_column | 说明 |")
    lines.append("|---|---|---|---|")
    for r in rules:
        if not all(r.get(k) for k in ("source_table", "source_column",
                                       "lookup_table", "lookup_key",
                                       "display_column")):
            continue  # 跳过缺字段的脏数据
        src = f"{r['source_table']}.{r['source_column']}"
        lkp = f"{r['lookup_table']} (key={r['lookup_key']})"
        desc = r.get("description") or ""
        lines.append(f"| {src} | {lkp} | {r['display_column']} | {desc} |")
    lines.append("")
    lines.append("统一要求：")
    lines.append("- SQL 涉及 source_column 时必须 LEFT JOIN lookup_table，按 lookup_key 关联")
    lines.append("- SELECT 一并带上 display_column AS <原列名>_name")
    lines.append("- 报告阶段：展示时用 display_column 替代 source_column")
    return "\n".join(lines)
```

**`build_schema_prompt`** `app/utils/prompt.py`：在 `prompt_instructions` 段之后追加：
```python
rules_text = render_display_rules_prompt(dataset.display_rules)
if rules_text:
    lines.append(rules_text)
    lines.append("")
```

**`report_generator_node`**：在 system 末尾追加（用 `state["dataset_display_rules_text"]`）：
```python
rules_text = state.get("dataset_display_rules_text") or ""
if rules_text.strip():
    system_content += "\n\n" + rules_text
```

**State** `app/graph/state.py`：加 `dataset_display_rules_text: Optional[str]`

**`schema_recall_node`**：写入：
```python
"dataset_display_rules_text": render_display_rules_prompt(ds.display_rules),
```

**`dsl_generate_node` 推断路径**：在 `dataset_prompt_instructions` 段附近追加：
```python
rules_text = state.get("dataset_display_rules_text") or ""
if rules_text.strip():
    human_text += "\n\n" + rules_text
```

#### Phase 3：前端 UI（最小可用版）

**dsForm**：
```js
const [dsForm, setDsForm] = useState({
  name: '', datasource_id: '', description: '',
  prompt_instructions: '',
  display_rules_text: '[]',  // 字符串形式，提交前 JSON.parse
});
```

**新建数据集弹窗**：在 `LLM 约束` Textarea 之后加一个"显示规则 (JSON)" Textarea：
```jsx
<FormField
  label="字段显示规则 (JSON, 可选)"
  type="textarea"
  rows={6}
  value={dsForm.display_rules_text}
  onChange={v => setDsForm({ ...dsForm, display_rules_text: v })}
  placeholder='[{"source_table":"plan_task_daily_record","source_column":"deptcode","lookup_table":"sys_dept","lookup_key":"dept_id","display_column":"dept_name","description":"部门编码→部门名称"}]'
/>
```

**`handleCreateDataset` payload**：
```js
let display_rules = [];
try { display_rules = JSON.parse(dsForm.display_rules_text || '[]'); }
catch { alert('显示规则 JSON 格式错误'); return; }
await createDataset({ ..., display_rules });
```

**"编辑约束"弹窗**：扩展为"编辑 LLM 约束 + 显示规则"双 Tab 或两段 Textarea。MVP 建议两段 Textarea，结构简单。

**reset**：`setDsForm({ ..., display_rules_text: '[]' })`

## 六、风险与缓解

| 风险 | 缓解 |
|---|---|
| LLM 还是不照 JOIN 规则做 | 规则段放在"硬性要求"标签下、system + human 双注入，调试可加 few-shot 真实示例 |
| 用户配的 JSON 格式错 | 渲染时跳过缺字段的脏数据；前端 JSON.parse 失败时 alert 阻止提交 |
| DisplayRuleItem 字段命名跟未来演进冲突 | 用 `source_*` / `lookup_*` / `display_*` 前缀，预留扩展（aggregations、formatters） |
| dataset 改字段加迁移 = 数据库 schema 变更 | 跟 `prompt_instructions` 一样做单列 op.add_column，向下兼容（旧库升级时 default=list 会触发 NULL 兼容逻辑） |
| 跟 metric/dimension 的 display_name 混淆 | 文档明确：`display_name` = 语义层名；`display_rules` = 物理表字段的运行时映射 |

## 七、跟现有机制的关系

| 机制 | 用途 | 关系 |
|---|---|---|
| `metric.display_name` | 指标的中文名 | 替代 |
| `dimension.display_name` | 维度的中文名 | 替代 |
| `source_column.effective_desc` | 字段标注的中文 | 替代 |
| `prompt_instructions` (Text) | 自由文本兜底规则 | 互补 |
| **`display_rules` (JSON)** | **结构化字段显示映射** | **本方案** |

**互补关系**：
- `display_rules` 处理"常见、规则化的字段映射"（多数情况）
- `prompt_instructions` 处理"一次性、特殊业务规则"（少数情况）
- 两者在 prompt 里都可见，互不冲突
