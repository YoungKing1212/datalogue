# 011 · Agentic Shell 第一阶段采用 Chat 入口加工作台协议

## 状态

- 状态：已敲定
- 时间：2026-06-26 12:01
- 触发：用户确认采用“现有 Chat 承接入口，但从数据结构和事件上按工作台设计”的混合模式

## 决策

第一版 Agentic Shell 先复用现有 Chat 页面承接入口，避免第一阶段前端大改；但任务模型、事件流、产物引用和状态结构按未来 BI 工作台设计，为后续独立工作台形态预留迁移口。

## 背景

在确认产品目标直接采用 C 形态后，需要决定用户从哪里进入 Agentic Shell。备选方向包括继续复用现有 Chat、新建独立 BI 工作台，或采用“Chat 入口 + 工作台协议”的混合模式。

当前数语已有可运行的 Chat / SSE / conversation_state / artifact 链路，第一阶段如果直接新建独立工作台，会把前端页面、任务状态、事件流、产物面板和后端协议同时推入实施范围，影响 BI 内核治理的优先级。

## 选择理由

- 复用现有 Chat 可以最大限度降低第一阶段前端改造成本，继续沿用已有用户路径和 `/chat/stream` 体验。
- 按工作台协议设计任务模型和事件结构，可以避免只做“对话增强”导致未来独立工作台返工。
- Chat 入口天然适合承接用户的自由表达；工作台协议则适合承接后续报告、图表、Python 分析、审计解释和多步骤任务。
- 该模式符合当前总路线：产品形态朝 C，但实施节奏保持稳，BI 查询内核仍按 B-governed 收紧。

## 被排除方案

- 只复用现有 Chat 且不设计工作台协议：短期最快，但会把 C-ready 退化成普通对话增强，后续接 ReportAgent / PythonAgent / AuditAgent 时容易重做事件和状态。
- 第一阶段直接新建独立 BI 工作台：产品形态更完整，但前端和状态管理成本过高，会分散能力清单、ToolAdapter、EventEnvelope 等核心治理工作的注意力。

## 对架构的影响

- 现有 Chat 页面成为第一版 Agentic Shell 的用户入口。
- `/chat/stream` 继续作为第一阶段主体验承载，但事件内容需要逐步映射到 `DatalogueEventEnvelope`。
- Chat 内部需要具备任务级结构：`task_id`、`task_type`、`task_status`、子任务事件、产物引用和可继续操作入口。
- 后续独立 BI 工作台只能消费同一套任务模型、事件协议和产物引用，不另起一套并行协议。
- 前端展示可以先从任务卡片、结果引用、报告草稿、审计解释入口开始，而不是一次性做完整工作台。

## 对开发计划的影响

- P5 的 Agentic Shell 产品入口改为已定方向：`Chat as Shell Entry, Workbench-ready Protocol`。
- M3 的 C 产品入口最小闭环需要优先打通 Chat 内的任务卡片、BI 结果引用、报告草稿和审计解释入口。
- `DatalogueEventEnvelope` 需要保留面向 Chat 的增量兼容，同时预留面向工作台时间线的任务事件结构。
- 前端第一阶段重点不是新增大页面，而是在现有 Chat 里承接任务状态、产物引用和继续操作入口。

## 后续问题

- Chat 内第一版任务卡片展示到什么粒度。
- 用户是否需要在 Chat 内看到完整任务时间线，还是只展示关键节点。
- 报告草稿、图表、审计解释是内嵌在回答区域，还是以右侧详情面板展开。
- 后续独立 BI 工作台从 Chat 中抽出时，URL、会话、任务和产物引用如何保持连续。
