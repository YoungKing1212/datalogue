# 端到端执行链路

## 一、问数流程全景

```
用户提问: "上个月销售额是多少？"
    │
    ▼
POST /api/agent-team/tasks/stream  (SSE)
    │
    ├─▶ AgentTeamTaskRuntime
    │    ├── 1. 创建 Datalogue task（数据库记录）
    │    ├── 2. 创建 AgentScope mirror 会话
    │    ├── 3. 写入用户消息
    │    └── 4. 委托给 Runner
    │
    ├─▶ AgentScopeServiceTaskRunner
    │    ├── 5. HTTP 调用 AgentScope Service
    │    │   ├── POST /agent → 创建/获取 Leader Agent
    │    │   ├── POST /sessions → 创建 session（绑定 model config）
    │    │   └── POST /chat → 触发聊天
    │    │
    │    ├── 6. AgentScope Service 内部执行
    │    │   ┌─────────────────────────────────────┐
    │    │   │ Agent Team 执行（AgentScope 官方机制）│
    │    │   │                                     │
    │    │   │ Leader Agent:                        │
    │    │   │   识别任务类型 → 规划 → 调用工具      │
    │    │   │   ├─ 路由到候选数据集                │
    │    │   │   ├─ AgentCreate → BI Worker Agent  │
    │    │   │   └─ TeamSay 等待 Worker 返回        │
    │    │   │                                     │
    │    │   │ BI Worker Agent:                     │
    │    │   │   通过 Tools 执行 BI 查询            │
    │    │   │   ├─ dataset_query tool              │
    │    │   │   ├─ generate_report tool            │
    │    │   │   └─ 结果输出                        │
    │    │   └─────────────────────────────────────┘
    │    │
    │    └── 7. 事件投影（AgentScope event → Datalogue envelope）
    │
    ├─▶ DatalogueEventEnvelope SSE 流
    │    ├── task.started
    │    ├── agent.selected
    │    ├── message.delta / reasoning.delta（增量文本）
    │    ├── tool_call.completed
    │    ├── artifact.created
    │    └── message.completed（终态）
    │
    └─▶ 前端消费 SSE，渲染对话
```

## 二、Leader Agent 控制面边界

Leader Agent 是当前主链控制面，必须保留在所有提速方案中。它负责理解任务、选择候选数据集、创建/协调 Worker、收敛 TeamSay 汇报和决定是否需要用户确认；BI Worker 只承担受控执行和私有诊断。`direct-query` 只能作为内部 fallback、开发调试或兼容入口，不能作为产品主入口，也不能绕过 Leader 直接面向用户承接问数请求。

Leader Agent 在 AgentScope Service 中可用的工具：

| 工具 | 说明 |
|------|------|
| **dataset_query** | 查询指定数据集（Datalogue 自定义工具） |
| **generate_report** | 生成分析报告 |
| **python_analysis** | Python 数据分析 |
| **AgentCreate** | 派生 Worker Agent（AgentScope 官方工具） |
| **TeamSay** | Worker 向 Leader 汇报结果 |
| **task_plan** | 任务规划与拆解 |
| **schedule** | 创建定时任务 |

## 三、BI Worker 执行内部

```
BI Worker 收到 dataset_query 任务
    │
    ▼
Datalogue Tool 层
    │
    ├─▶ BIWorkerQueryRuntime.execute_query_plan()
    │    ├── 上下文与关系校验: BIWorkerQueryValidator
    │    │   ├── 检查 query_plan 是否被渐进式上下文支持
    │    │   └── 不支持的 → 返回 RepairRequest / RepairPlanCard
    │    │
    │    ├── QueryPlan 受控执行
    │    │   ├── AgentScopeDatasetRuntimeBridge
    │    │   ├── BI Atomic Toolkit
    │    │   │   ├── 语义资产解析（指标/维度/术语）
    │    │   │   ├── DSL 生成（结构化查询描述）
    │    │   │   ├── SQL 编译（SQLGlot 方言转换）
    │    │   │   ├── SQL 执行（通过数据源连接）
    │    │   │   └── 结果解释 → 报告生成
    │    │   └── 异常 → RepairRequest / checkpoint_ref
    │    │
    │    └── 返回 QueryResult / RepairRequest
    │
    ▼
AgentScope event → Datalogue event projection
    → SSE 投递到前端
```

## 四、Repair 一等链路

repair 不是错误提示补丁，而是问数可信闭环。执行链路中只要出现 QueryPlan 契约错误、上下文证据不足、join/relationship 不可支持、数据库执行失败或 artifact 写入异常，都必须进入以下阶段：

1. **Failure Classifier**：把失败归类为契约错误、上下文不足、关系不可支持、执行异常或产物异常。
2. **Private Diagnosis**：runtime/tool 私有诊断层可读取 SQL、schema、raw rows、原始数据库报错和本地 debug 线索，但这些内容不得进入 LLM prompt、用户可见 SSE、artifact 摘要或 OpenViking 普通上下文。
3. **Repair Planner**：生成脱敏的 RepairRequest / RepairPlanCard，只暴露业务原因、安全摘要、可确认选项和 `checkpoint_ref` / `artifact_ref` 等 refs。
4. **User Confirmation**：涉及口径、候选数据集、字段映射或重试成本时，必须让用户确认，而不是由 Worker 继续猜。
5. **Retry Executor**：用户确认后基于 checkpoint/ref 续跑，继续通过 Leader 控制面协调。
6. **Artifact Writer**：成功或失败都写入可审计产物或状态，前端通过 Workbench / artifact API 查看，不把 raw rows 直接塞进聊天正文。

## 五、Manifest 路由流程

```
用户提问
    │
    ▼
LeadAgent 调用 Manifest 路由工具
    │
    ├─▶ 对所有 current Manifest 打分（score_manifest_question）
    │    ├── 阈值 0.65，领先差 0.12
    │    └── 结果: locked / selected / ambiguous / no_match
    │
    ├─▶ locked → 直接使用该数据集
    ├─▶ selected → 自动选择最高分数据集
    ├─▶ ambiguous → 返回候选列表给用户确认
    └─▶ no_match → 提示无法匹配
```

## 六、QueryPlan 与 legacy DSL 退出方向

QueryPlan 是 BI Worker Agent 与 Datalogue Tools 之间的当前 Worker 契约；legacy DSL / legacy query plan 仅属于执行器兼容层，这项转换仍是明确的迁移债务。短期继续用转换层承接既有 SQL 编译和执行能力，但每次新增字段、聚合、筛选、排序或 join 支持时，都必须同步测试 QueryPlan 到兼容层的映射，避免 repair 无法区分 QueryPlan 错、转换错还是 SQL 编译错。`ControlledQuerySpec` 是未来核心路径，中期目标是让执行器直接消费 QueryPlan 或统一到该契约。

当前 assistant-ui 只补齐稳定结果卡、reasoning summary 和 ThreadList 的消息恢复；禁止做 headless primitives 级大重构，也不重写 assistant-ui runtime，待问数事件协议与回放契约持续稳定后再评估。

## 七、事件协议

### DatalogueEventEnvelope 字段

| 字段 | 类型 | 说明 |
|------|------|------|
| `event_type` | string | 事件类型 |
| `task_id` | string | 任务 ID |
| `trace_id` | string | 追踪 ID |
| `thread_id` | string | 会话 ID |
| `message_id` | string | 消息 ID |
| `selected_agent` | string | 当前 Agent |
| `payload` | dict | 事件负载 |
| `legacy_payload` | dict | 前端兼容负载 |

### 事件三层分流

| 分层 | 事件职责 | 代表内容 |
|------|----------|----------|
| 用户可见事件 | 聊天 UI 只消费安全业务进度和最终结果 | `message.delta`、`message.completed`、`artifact.created`、候选确认 |
| Workbench 事件 | 支撑 checkpoint、retry、artifact 和线程视图 | `checkpoint_ref`、`artifact_ref`、`trace_ref`、retry action |
| Debug 事件 | 支撑开发者定位 Leader / Worker / Tool / DB 问题 | raw debug、private diagnosis、tool trace、DB 原始错误 |

`legacy_payload` 只作为前端兼容字段冻结保留，不再扩字段；新增事件字段必须先归入上述三层之一。SQL、schema、raw rows、原始报错和 private diagnosis 默认只属于 Debug 事件，不进入用户可见 SSE。

### 事件类型

| 类型 | 说明 |
|------|------|
| `task.started` | 任务已启动 |
| `agent.selected` | Agent 已选定 |
| `message.delta` | 消息增量（流式文本） |
| `reasoning.delta` | 推理增量 |
| `tool_call.completed` | 工具调用完成 |
| `dataset.selected` | 数据集已选定 |
| `clarification.required` | 需要用户澄清 |
| `artifact.created` | 查询产物已创建 |
| `message.completed` | 最终回答 |
| `task.completed` | 任务完成 |
| `task.failed` | 任务失败 |
