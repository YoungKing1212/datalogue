# 目录治理与模块边界

> Phase A 交付物。本文只定义目录职责、目标边界和渐进迁移决策，不移动源代码、不改导入路径、不删除文件。

## 1. 背景与目标

Datalogue 当前已经形成 AgentScope 主链、Agent Team 任务运行、BI Worker 查询执行、assistant-ui 前端工作台和文档资产多线并行的结构。随着功能快速迭代，部分目录以技术层命名，部分目录以历史阶段命名，容易出现以下问题：

- 同一业务概念跨 `services`、`agentscope_service`、`runtime`、`bi`、`events` 多处落点，新增能力时难以判断应放在哪一层。
- 前端 assistant-ui 适配、后端 AgentScope 运行时和 BI Worker 查询产物之间存在跨层状态写入，缺少统一边界说明。
- `docs`、`outputs`、`logs`、`wheelhouse` 等交付物、运行产物和离线依赖容易混放，影响审计和发布判断。

本次目录治理的目标是先形成“当前职责 - 目标职责 - 迁移规则”的稳定协议，为后续 facade-first（门面优先）的渐进迁移提供依据。

### 明确不改变的边界

- 不改变 AgentScope 主链：Leader / Agent Team / Workbench 的主链路、事件语义、消息持久化和 retry 恢复策略保持不变。
- 不改变 BI Worker 查询语义：QueryPlan、DSL、SQL 执行、artifact/ref 回传和安全摘要边界保持不变。
- Phase A 不移动源代码：本文只产出治理文档和目录快照，不重命名目录、不改导入、不删除历史文件。

## 2. 当前目录职责矩阵

### 2.1 后端 `datalogue-api/app`

| 当前目录 | 当前职责 | 主要边界 | 当前治理风险 |
| --- | --- | --- | --- |
| `app/api` | FastAPI 路由入口，承接会话、数据源、Workbench、任务流等 HTTP/SSE 接口。 | 只应做请求解析、权限/依赖注入、调用应用服务、返回响应。 | 容易把业务编排和响应组装直接写入路由，导致接口层过厚。 |
| `app/services` | 应用服务层，承载数据源管理、Workbench 视图模型、镜像同步、业务编排等。 | 负责事务边界、跨模型读写、调用运行时或领域能力。 | 服务职责跨度较大，既有数据源能力，也有 AgentScope mirror/view model 能力。 |
| `app/agentscope_service` | AgentScope / Agent Team 相关运行、注册、任务执行和对外服务封装。 | 负责 AgentScope 框架接入和 Agent Team task runtime 的运行桥接。 | 与 `runtime`、`services` 的边界需要明确，避免运行时状态和业务视图互相穿透。 |
| `app/agents` | 传统或专用 Agent 实现，包括 BI Agent 等历史能力。 | 放智能体实现、prompt 协调和旧链路兼容代码。 | 与 AgentScope 新主链存在历史重叠，后续应避免新增主链能力落到旧 agent 目录。 |
| `app/bi` | BI Worker 工具链、原子工具、技能、查询执行相关能力。 | 负责 QueryPlan/DSL/SQL/artifact 的 worker-private 查询语义。 | 需防止把通用 Agent Team 编排或 API 响应逻辑放入 BI 专属目录。 |
| `app/models` | SQLAlchemy 持久化模型，包括会话、AgentScope mirror、任务、数据源等表结构。 | 只描述数据库结构和 ORM 关系，不承载业务流程。 | 模型数量增加后需要按领域归属管理依赖，避免模型层反向调用服务层。 |
| `app/schemas` | Pydantic 请求/响应/契约模型。 | 负责 API 和内部契约的数据结构，不应执行外部副作用。 | 容易混入运行时默认值或业务计算，后续应与领域 contract 分层。 |
| `app/core` | 配置、数据库连接、基础设施初始化等核心支撑。 | 放跨域基础设施能力，例如 settings、database、日志/追踪初始化。 | 不应放领域业务逻辑，否则会形成全局依赖中心。 |
| `app/utils` | 通用工具函数。 | 放无状态、无领域归属、低副作用的通用辅助函数。 | 容易成为杂物箱；若工具只服务某领域，应迁回对应领域。 |
| `app/events` | 事件投影、Workbench/AgentScope 事件处理相关能力。 | 负责事件到视图/持久层的投影与转换。 | 与 `services` 的 view model / mirror 职责相邻，需要防止重复写同一状态。 |
| `app/runtime` | 运行时适配与 Agent Team runtime。 | 放运行时生命周期、任务执行上下文和框架桥接。 | 与 `agentscope_service` 需要通过 facade 收敛调用入口。 |

### 2.2 前端 `datalogue-web/src`

| 当前目录 | 当前职责 | 主要边界 | 当前治理风险 |
| --- | --- | --- | --- |
| `src/components` | 通用和业务 UI 组件，包括页面块、工作台部件、列表、表单等。 | 负责展示和轻量交互，不直接承载主链协议。 | 容易把接口适配和状态投影写进组件，后续应抽到 feature/adapters。 |
| `src/assistant` | Datalogue 对 assistant-ui 的业务适配，包括 ThreadList、消息投影、运行时桥接。 | 负责把后端会话/Workbench 数据映射为 assistant-ui 可消费结构。 | 与 `assistant-ui` 基础组件边界相邻，需避免把 UI primitive 改造成业务状态源。 |
| `src/assistant-ui` | assistant-ui 组件封装、样式和项目级 UI 组合。 | 放 assistant-ui 的界面组合、主题和可复用壳层。 | 不应直接写后端协议细节，否则后续升级 assistant-ui 成本变高。 |
| `src/api` | 前端 API 调用入口。 | 封装 HTTP/SSE 请求、错误处理和后端 endpoint 访问。 | 当 client/adapters 不清晰时，组件会绕过统一 API 直接请求后端。 |
| `src/api/client/adapters` | 目标上应承载 API client 和业务适配器；当前需逐步从 assistant 适配代码中抽取。 | 负责把后端 DTO 转成前端领域对象或 assistant-ui message parts。 | 若缺少统一约定，会导致 Workbench、ThreadList、message parts 多处重复转换。 |

### 2.3 文档与运行产物

| 当前路径 | 当前职责 | 主要边界 | 当前治理风险 |
| --- | --- | --- | --- |
| `docs` | 架构、计划、上下文入口、阶段交付、设计材料。 | 放可版本化、可审计的项目知识和决策记录。 | 若所有临时材料都进入 docs，长期会降低入口可读性。 |
| `outputs` | 运行输出、分析结果、临时导出或验收产物。 | 放可复现或需要交付引用的输出，不应作为源码依赖。 | 容易积累过期产物，后续需要 archive 策略。 |
| `logs` | 运行日志或调试日志。 | 只作为排障证据，不应成为业务状态来源。 | 若日志进入版本库或被文档引用为长期事实，容易过期。 |
| `wheelhouse` | 离线 Python 依赖包或构建缓存。 | 只服务离线部署/构建，不承载业务代码。 | 体积和版本漂移风险较高，需要和源码、docs 明确隔离。 |

## 4. ADR：采用 facade-first 渐进迁移

### 4.1 决策

采用 facade-first 渐进迁移，不做一次性重命名。

含义：先在目标域建立稳定 facade（门面入口）和契约文档，让新代码通过 facade 调用旧实现；待调用路径稳定、测试覆盖充分后，再逐步把旧实现移动到目标域内部。Phase A 只完成文档和快照，不进行任何源码移动。

### 4.2 选择理由

- AgentScope 主链和 BI Worker 查询语义仍在快速收口，一次性重命名会扩大导入路径风险。
- 当前已有前后端、日志、artifact、Workbench view model 等多层验证链路，渐进 facade 可以把验证范围控制在单个领域。
- 允许保留历史目录，降低与用户/其他工具已有改动冲突的概率。

### 4.3 迁移顺序

1. 建立目录职责协议：维护本文和当前目录快照，明确每个目标域 owner、职责和禁止放入内容。
2. 新增 facade 入口：优先为 `data_source`、`agent_team`、`bi`、`query_execution` 建立薄门面，门面只转发到现有实现并补契约测试。
3. 新代码先走 facade：新增 API、服务或前端适配不得直接扩大旧目录职责，优先调用目标域 facade。
4. 按领域抽离实现：每次只迁移一个小闭环，例如数据源 capability、BI artifact、Agent Team task projection。
5. 清理旧路径：只有当调用方、测试、运行验证都通过后，才移除旧入口或改为兼容壳。
6. 文档同步：每次完成迁移后更新职责矩阵和 `.codex/project-memory.md`；若只是 Phase A 文档产出，则不更新项目记忆。

### 4.4 停止条件

任一条件出现时，必须暂停迁移，只保留兼容 facade，不继续移动实现：

- AgentScope 主链的会话创建、任务流、Workbench 展示或 retry 恢复出现回归。
- BI Worker 的 QueryPlan、DSL、SQL、artifact/ref 回传语义发生变化或无法解释差异。
- 前端 assistant-ui ThreadList、message parts、Workbench 侧栏出现状态源不一致。
- 测试需要大规模改快照但无法证明业务语义未变。
- Git 状态显示非目标源码移动、删除或大量重命名，且无法确认是当前迁移所需。

### 4.5 验证矩阵

| 验证层 | 验证内容 | Phase A 要求 | 后续迁移要求 |
| --- | --- | --- | --- |
| 文件边界 | 只写指定文档和快照。 | 检查两个文件存在，`git diff -- docs/architecture/目录治理与模块边界.md .omx/context/directory-planning/current-directory-snapshot.md`。 | 每次迁移前后检查 `git status --short`，确认移动范围可解释。 |
| AgentScope 主链 | 会话、Agent Team task、事件流、Workbench view model、retry。 | 不触碰源码，因此只声明不改变。 | 跑后端相关测试和真实 SSE/Workbench smoke。 |
| BI Worker 查询语义 | QueryPlan、DSL、SQL 执行、artifact/ref、安全摘要。 | 不触碰源码，因此只声明不改变。 | 跑 BI Worker contract/unit 测试，并核对 artifact payload。 |
| 前端 assistant-ui | ThreadList、message parts、Workbench 侧栏、API adapter。 | 不触碰源码，因此只声明目标边界。 | 执行 `npm run lint`、`npm run build`，必要时做桌面 E2E 截图验收。 |
| 文档一致性 | 目录快照、职责矩阵、ADR 一致。 | 本文与快照同时提交。 | 迁移后同步职责矩阵和上下文入口。 |
