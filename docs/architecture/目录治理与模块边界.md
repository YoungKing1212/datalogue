# 目录治理与模块边界

> Phase A 交付物。本文只定义目录职责、目标边界和渐进迁移决策，不移动源代码、不改导入路径、不删除文件。

## 1. 背景与目标

Datalogue 当前已经形成 AgentScope 主链、Agent Team 任务运行、BI Worker 查询执行、assistant-ui 前端工作台和文档资产多线并行的结构。随着功能快速迭代，部分目录以技术层命名，部分目录以历史阶段命名，容易出现以下问题：

- 同一业务概念跨 `services`、`agentscope_service`、`runtime`、`bi`、`events` 多处落点，新增能力时难以判断应放在哪一层。
- 前端 assistant-ui 适配、后端 AgentScope 运行时和 BI Worker 查询产物之间存在跨层状态写入，缺少统一边界说明。
- `docs`、`outputs`、`logs`、`wheelhouse` 等交付物、运行产物和离线依赖容易混放，影响审计和发布判断。

本次目录治理的目标是先形成“当前职责 - 目标职责 - 迁移规则”的稳定协议，为后续 facade-first（门面优先）的渐进迁移提供依据。

### 明确不改变的边界

- 不改变 AgentScope 主链：Leader / Agent Team / Workbench 的主链路、事件语义、消息持久化和 retry 恢复策略保持不变。
- 不改变 BI Worker 查询语义：QueryPlan、DSL、SQL 执行、artifact/ref 回传和安全摘要边界保持不变。
- Phase A 不移动源代码：本文只产出治理文档和目录快照，不重命名目录、不改导入、不删除历史文件。

## 2. 当前目录职责矩阵

### 2.1 后端 `datalogue-api/app`

| 当前目录 | 当前职责 | 主要边界 | 当前治理风险 |
| --- | --- | --- | --- |
| `app/api` | FastAPI 路由入口，承接会话、数据源、Workbench、任务流等 HTTP/SSE 接口。 | 只应做请求解析、权限/依赖注入、调用应用服务、返回响应。 | 容易把业务编排和响应组装直接写入路由，导致接口层过厚。 |
| `app/services` | 应用服务层，承载数据源管理、Workbench 视图模型、镜像同步、业务编排等。 | 负责事务边界、跨模型读写、调用运行时或领域能力。 | 服务职责跨度较大，既有数据源能力，也有 AgentScope mirror/view model 能力。 |
| `app/agentscope_runtime` | AgentScope / Agent Team 相关运行、注册、任务执行和对外服务封装。 | 负责 AgentScope 框架接入、Agent Team task runtime 桥接、Service 子应用生命周期和事件投影。 | 与 `runtime`、`domains/agent_team` 的边界需要明确，避免运行时状态和业务视图互相穿透。 |
| `app/domains/bi/agent` | BI Agent 领域入口，当前承载 runtime context 与 native handoff。 | 只组装 BI Worker 使用 Dataset 工具链所需的运行时上下文，不拥有 AgentScope Service 生命周期。 | 不得重新引入旧 `app/agents/bi_agent` 入口或把通用 Agent Team 编排放入 BI Agent 目录。 |
| `app/domains/bi/skill` / `app/domains/bi/toolkit` | BI Worker Skill、Runtime Bridge、原子工具、查询执行相关能力。 | 负责 QueryPlan/DSL/SQL/artifact 的 worker-private 查询语义和受控工具注册。 | 需防止把 raw SQL、未清洗 rows、通用 Agent Team 编排或 API 响应逻辑暴露到用户可见层。 |
| `app/models` | SQLAlchemy 持久化模型，包括会话、AgentScope mirror、任务、数据源等表结构。 | 只描述数据库结构和 ORM 关系，不承载业务流程。 | 模型数量增加后需要按领域归属管理依赖，避免模型层反向调用服务层。 |
| `app/schemas` | Pydantic 请求/响应/契约模型。 | 负责 API 和内部契约的数据结构，不应执行外部副作用。 | 容易混入运行时默认值或业务计算，后续应与领域 contract 分层。 |
| `app/core` | 配置、数据库连接、基础设施初始化等核心支撑。 | 放跨域基础设施能力，例如 settings、database、日志/追踪初始化。 | 不应放领域业务逻辑，否则会形成全局依赖中心。 |
| `app/utils` | 通用工具函数。 | 放无状态、无领域归属、低副作用的通用辅助函数。 | 容易成为杂物箱；若工具只服务某领域，应迁回对应领域。 |
| `app/events` | 事件投影、Workbench/AgentScope 事件处理相关能力。 | 负责事件到视图/持久层的投影与转换。 | 与 `services` 的 view model / mirror 职责相邻，需要防止重复写同一状态。 |
| `app/runtime` | 运行时适配与 Agent Team runtime。 | 放运行时生命周期、任务执行上下文和框架桥接。 | 与 `agentscope_service` 需要通过 facade 收敛调用入口。 |

## 4. ADR：采用 facade-first 渐进迁移

### 4.1 决策

采用 facade-first 渐进迁移，不做一次性重命名。

含义：先在目标域建立稳定 facade（门面入口）和契约文档，让新代码通过 facade 调用旧实现；待调用路径稳定、测试覆盖充分后，再逐步把旧实现移动到目标域内部。Phase A 只完成文档和快照，不进行任何源码移动。

### 4.1.1 G055 物理搬迁决策

截至 G055，暂不启动 AgentScope runtime、Agent Team、BI runtime 或前端目录的物理文件搬迁。

G049-G054 已完成 facade-first 迁移顺序中的步骤 2-3：建立目标 facade 入口，并把已有测试覆盖的生产调用方切到新 facade。当前已经完成的工作属于 facade-first 与调用方迁移：

- `app.agentscope_runtime` 已成为 AgentScope Service 嵌入、runner、registry、projection、OTel、worker logging、client 与 credential 的稳定新入口。
- `app.domains.bi` 已明确为 BI runtime context、Skill、Toolkit、Worker QueryPlan 契约和运行时的 canonical owner。
- `app.domains.agent_team` 已明确为 Datalogue 对外 task、Workbench view/retry action、event envelope 的业务真相源。
- 已有测试覆盖的生产调用方可以切到新 facade，但旧实现文件仍保留在原路径，避免一次性扩大 import、启动顺序和测试 blast radius。

物理搬迁的开放条件如下；未同时满足前，不移动旧实现文件：

1. G056-G059 的 Agent Team stream、AgentScope Service 关键子集、BI native handoff、Workbench retry/action/view 回归全部通过。
2. 主工作区没有与目标迁移文件重叠的未提交改动；若存在临时业务边界改动，必须先单独收口测试期望。
3. 每个待移动模块已有旧路径兼容壳或 deprecation facade，且静态导入测试能证明新旧入口同时可用。
4. 物理移动只按一个 owner 域一个小闭环执行，例如先移动只读 projection，再移动 registry 或 runner，不能跨 AgentScope runtime、BI、Agent Team、前端同时搬迁。

G056-G059 的具体验收标准如下，作为后续重新评估物理搬迁的可审计闸门：

- G056（Agent Team stream）：`/api/agent-team/tasks/stream` 的任务创建、SSE 事件流、Agent Team 消息回放和关闭路径回归通过。
- G057（AgentScope Service 关键子集）：embedded runtime 启动、worker registry、client、projection、worker logging、LLM credential 注入和 OTel trace 投影关键测试通过。
- G058（BI native handoff）：BI Lead Agent 到 BI Worker 的 native handoff、runtime context 组装、QueryPlan 执行入口和 artifact/ref 安全回传回归通过。
- G059（Workbench retry/action/view）：Workbench retry/action/view model 的 task request、checkpoint/ref、只读旧会话和用户可见 envelope 投影回归通过。

因此 G055 的结论是：继续保持 facade-first 状态，把后续故事优先用于验证闸门和调用方收口；物理搬文件需要在这些闸门之后重新评估并单独提交。

### 4.1.2 G060 前端 `src/app` 应用壳规划

截至 G060，前端先新建 `datalogue-web/src/app/README.md` 作为应用壳规划入口，不搬迁 `src/App.jsx`、`src/components/sidebar.jsx` 或任何页面源码。

当前有效归属如下：

- `src/App.jsx` 继续承载 `App`、`AppInner`、`TopBar`、`RequireAuth`、`RequireSuperuser`、`ErrorBoundary`、路由表、面包屑和应用级主题 tweak。
- `src/components/sidebar.jsx` 继续承载 `Sidebar`、导航分组、active 规则、新会话入口和用户管理权限显示。
- `src/app` 只记录目标边界，作为后续拆分时的应用壳 owner，不直接承接后端 DTO、assistant-ui message part 投影、BI 查询语义或 Workbench 业务状态机。

后续拆分顺序必须保持可回滚的小闭环：

1. 先抽取 `navigation.js` 这类纯配置，统一侧栏分组与顶部面包屑，避免两个路由文案源继续漂移。
2. 再抽取 `topbar.jsx` 和 `sidebar.jsx`，迁移期先在 `src/app` 建薄 re-export 入口，待调用方收口后再移动源码，避免一次性扩大 import blast radius。
3. 再抽取 `routes.jsx`、`app-shell.jsx` 和 `app-root.jsx`；`RequireAuth` 优先保留在 `app-root.jsx` 包裹主壳，`RequireSuperuser` 优先跟随 `routes.jsx` 的管理员路由配置，保持 `/login`、`/chat/:id`、`/workbench/:threadId`、`/workbench/:threadId/:artifactRef`、`/users` 等现有路径和鉴权语义不变。
4. 源码拆分故事必须执行 `npm run lint`、`npm run build`、`npm run test`；触达真实 UI 行为时，还要做桌面视口 smoke，验证登录跳转、侧栏 active、顶部面包屑和 Workbench 深链。

G060 的结论是：`src/app` 可以作为前端应用壳目标域，但当前只落规划文档；实际拆文件留给后续独立故事执行。

### 4.2 选择理由

- AgentScope 主链和 BI Worker 查询语义仍在快速收口，一次性重命名会扩大导入路径风险。
- 当前已有前后端、日志、artifact、Workbench view model 等多层验证链路，渐进 facade 可以把验证范围控制在单个领域。
- 允许保留历史目录，降低与用户/其他工具已有改动冲突的概率。

### 4.3 迁移顺序

1. 建立目录职责协议：维护本文和当前目录快照，明确每个目标域 owner、职责和禁止放入内容。
2. 新增 facade 入口：优先为 `data_source`、`agent_team`、`bi`、`query_execution` 建立薄门面，门面只转发到现有实现并补契约测试。
3. 新代码先走 facade：新增 API、服务或前端适配不得直接扩大旧目录职责，优先调用目标域 facade。
4. 按领域抽离实现：每次只迁移一个小闭环，例如数据源 capability、BI artifact、Agent Team task projection。
5. 清理旧路径：只有当调用方、测试、运行验证都通过后，才移除旧入口或改为兼容壳。
6. 文档同步：每次完成迁移后更新职责矩阵和 `.codex/project-memory.md`；若只是 Phase A 文档产出，则不更新项目记忆。

### 4.4 停止条件

任一条件出现时，必须暂停迁移，只保留兼容 facade，不继续移动实现：

- AgentScope 主链的会话创建、任务流、Workbench 展示或 retry 恢复出现回归。
- BI Worker 的 QueryPlan、DSL、SQL、artifact/ref 回传语义发生变化或无法解释差异。
- 前端 assistant-ui ThreadList、message parts、Workbench 侧栏出现状态源不一致。
- 测试需要大规模改快照但无法证明业务语义未变。
- Git 状态显示非目标源码移动、删除或大量重命名，且无法确认是当前迁移所需。
