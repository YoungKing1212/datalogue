# 004 · can_answer 等能力文案采用模型辅助生成加人工审核

## 状态

- 状态：已敲定
- 时间：2026-06-26 11:07
- 触发：用户确认“可以，我也倾向于这个”

---

## 决策

`can_answer`、`cannot_answer`、`typical_questions` 等能力文案采用：

```text
模型辅助生成 + 人工审核，发布时固化
```

模型负责根据数据集名称、描述、指标/维度摘要、业务术语、已发布 Manifest 和治理信息生成候选能力文案；人工负责审核、修订、确认和发布。发布后的内容作为 `static_capability` 的一部分固化，不在每次查询请求中临时生成。

---

## 背景

前面已经确认：

```text
001：capability_manifest 定位为轻量能力广告
002：capability_manifest 采用固化主体 + 运行态叠加
003：static_capability 字段边界只到业务摘要层
```

在这个前提下，需要明确 `static_capability` 中最关键的能力文案由谁生成和审核。这里的内容会直接影响 LeadAgent 的数据集路由、拒答判断、澄清策略和未来外层 Agentic Shell 的能力发现。

---

## 选择理由

选择“模型辅助生成 + 人工审核”的原因：

- 纯人工维护成本高，容易漏写典型问题和不可回答范围。
- 纯模型生成不够可信，可能夸大能力或生成未被治理确认的边界。
- 人工审核可以把能力文案纳入数据集发布流程，形成可审计版本。
- 发布时固化可以保证路由依据稳定，便于测试、回放和问题定位。
- 模型适合做初稿、同义表达补全和典型问题扩展，但不能拥有最终发布权。

---

## 被排除方案

### 方案一：完全人工维护

未采用。

原因：

- 成本高，更新慢。
- 很难系统性覆盖不可回答范围和典型问法。
- 数据集数量增加后维护压力会快速上升。

### 方案二：完全模型自动生成并直接生效

未采用。

原因：

- 可能夸大数据集能力。
- 可能把未治理、未授权或不稳定的能力暴露给 LeadAgent。
- 不利于审计，也不适合企业问数生产链路。

### 方案三：每次请求时动态生成

未采用。

原因：

- 路由依据不稳定，难以回放。
- 请求成本更高。
- 容易把运行时上下文和发布态能力混在一起。

## 对架构的影响

能力文案生成流程建议为：

```text
数据集治理信息 / Manifest / 语义资产摘要
  -> 模型生成候选 static_capability 文案
  -> 人工审核和修订
  -> 发布并固化版本
  -> LeadAgent / Agentic Shell 读取发布态能力广告
```

模型可以参与：

```text
can_answer 初稿
cannot_answer 初稿
typical_questions 初稿
routing_hints 初稿
业务同义词补全建议
```

人工必须确认：

```text
能力是否真实覆盖
不可回答范围是否明确
典型问题是否符合业务口径
是否暴露了不该暴露的字段、表、SQL 或 blueprint 主体
是否符合当前发布版本的 Manifest 和权限边界
```

## 对开发计划的影响

后续至少需要拆出这些任务：

- 设计能力文案生成入口。
- 设计能力文案审核和发布状态。
- 将 `can_answer`、`cannot_answer`、`typical_questions`、`routing_hints` 纳入数据集发布流程。
- 增加能力文案版本号和更新时间。
- 增加生成候选内容的安全扫描，禁止字段、表、SQL、blueprint 主体进入发布态能力广告。
- 增加人工审核后的快照测试。
- 定义能力文案变更对 LeadAgent 路由回归测试的影响。
