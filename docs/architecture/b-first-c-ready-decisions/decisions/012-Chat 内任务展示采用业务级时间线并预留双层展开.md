# 012 · Chat 内任务展示采用业务级时间线并预留双层展开

## 状态

- 状态：已敲定
- 时间：2026-06-26 12:06
- 触发：用户确认“可以定”，并要求记录方案 3 的后续改造

## 决策

Chat 内第一版任务展示采用业务级任务时间线；默认只展示用户可理解的任务节点、数据集选择、执行状态、结果引用和下一步动作。事件协议和状态模型必须预留方案 3 的双层可展开时间线能力，后续升级为“默认业务节点 + 可展开受控技术摘要”。

## 背景

在确认第一版 Agentic Shell 复用现有 Chat 入口后，需要决定 Chat 内如何呈现 C 形态的任务结构。备选方向包括极简状态卡、业务级任务时间线、可展开双层时间线。

本轮选择不是只做加载状态，也不是第一阶段直接做完整审计级展开，而是在用户体验和后续工作台演进之间取平衡。

## 选择理由

- 业务级任务时间线能让用户理解系统正在做什么，例如理解问题、匹配数据集、查询数据、生成摘要、提供下一步动作。
- 第一阶段不默认展示 SQL、schema、raw result、trace 或 `control_plane` 主体，符合 B-governed BI 内核边界。
- 比极简状态卡更接近 C 产品形态，也更容易承接报告、分析、审计解释等后续动作。
- 双层可展开时间线对未来审计、管理员视图和开发排障有价值，因此必须在事件协议和状态模型中预留，而不是后续另起一套。

## 被排除方案

- 只做极简状态卡：实现最简单，但产品上仍像普通 Chat loading，不足以承接 C 形态的任务编排和产物引用。
- 第一阶段直接做完整双层展开：能力最完整，但会过早放大前端展示、权限分层、脱敏和事件粒度设计成本，容易拖慢 BI 内核治理。

## 对架构的影响

- `DatalogueEventEnvelope` 第一阶段需要覆盖业务级节点：任务理解、数据集匹配、BI 执行、结果产物、下一步动作。
- 每个业务节点都要具备稳定的 `event_type`、`task_id`、`visibility`、`status` 和引用字段。
- 事件协议需要预留 `details` 或同等扩展位，用于后续双层展开展示受控技术摘要。
- `details` 只能承载脱敏摘要，例如能力清单匹配依据、guard 状态、artifact 引用、trace 关联摘要；不得直接暴露 raw SQL、raw result、schema、capsule 或 `control_plane` 主体。
- AuditAgent 后续可以消费同一套事件和 artifact 摘要生成解释，不需要重新定义一套审计事件。

## 对开发计划的影响

- M3 第一阶段落地业务级任务时间线，重点是用户可见节点和下一步动作。
- M4/M5 必须记录并推进双层可展开时间线改造，包括权限分层、脱敏规则、可展开技术摘要和审计视图。
- 前端第一阶段可以先实现任务卡片，不需要一次性做完整工作台详情面板。
- 事件协议设计时不能只满足当前 UI，必须保留后续 `expandable_details` / `technical_summary` 的扩展点。

## 后续问题

- 第一版业务级任务节点最终命名和数量。
- 哪些节点需要提供下一步动作按钮。
- 双层展开的受控技术摘要面向普通用户、管理员、开发者是否分三种可见级别。
- `technical_summary` 是由后端规则生成，还是由 AuditAgent 基于 artifact 和 trace 生成。
