# 013 · 产物详情采用 Chat 轻量卡并预留详情面板

## 状态

- 状态：已敲定
- 时间：2026-06-26 12:10
- 触发：用户确认采用“Chat 内轻量产物卡 + 预留详情面板/工作台承载完整产物”的方案

## 决策

第一阶段报告草稿、图表、审计解释等产物在 Chat 内采用轻量产物卡承载；默认只展示摘要、引用和下一步动作。完整产物详情通过 `detail_view_ref` / `artifact_panel_ref` 或同等引用预留，后续升级为右侧详情面板或独立 BI 工作台承载。

## 背景

前面已经确认第一阶段复用现有 Chat 作为 Agentic Shell 入口，并在 Chat 内展示业务级任务时间线。接下来需要决定报告、图表、审计解释等“产物详情”放在哪里。

如果完整产物全部塞进 Chat 消息，短期实现直接，但会让对话流迅速臃肿，也不利于后续迁移到 BI 工作台。如果第一阶段直接做右侧详情面板，则前端改造成本较高。

## 选择理由

- Chat 轻量卡能保持当前入口简洁，避免长报告、大表格、复杂图表和完整审计链路淹没对话流。
- 摘要、引用和动作入口足以支撑第一阶段 C 形态体验：用户能看到产物已生成，也能继续编辑、分析、解释或导出。
- `detail_view_ref` / `artifact_panel_ref` 为后续详情面板和独立工作台提供稳定迁移口。
- 完整产物继续通过 artifact / ref 管理，符合 BI 内核可审计、可回放、可脱敏的边界。

## 被排除方案

- 全部内嵌在回答区：第一阶段实现直接，但对话会变重，长报告、图表和审计解释难以管理。
- 第一阶段直接做右侧详情面板：产品形态更完整，但会拉高前端状态、布局、移动端适配和产物切换成本。

## 对架构的影响

- Chat 消息中的产物卡只承载轻量摘要、产物类型、引用句柄和下一步动作。
- 完整报告、图表、审计解释必须通过 `result_ref`、`report_ref`、`chart_ref`、`audit_ref`、`detail_view_ref` 或 `artifact_panel_ref` 等引用访问。
- 产物卡不能直接包含完整表格、完整报告正文、完整审计链路、raw SQL、raw result、schema、capsule 或 `control_plane` 主体。
- 前端后续详情面板和独立 BI 工作台必须复用同一套产物引用，不重新定义一套内容承载协议。
- `DatalogueEventEnvelope` 需要能表达产物创建、产物摘要可见、详情引用可用和下一步动作可用。

## 对开发计划的影响

- M3 第一阶段只要求在 Chat 内落地轻量产物卡和下一步动作入口。
- M4/M5 记录后续升级为右侧详情面板或独立 BI 工作台，用于承载完整报告、图表、审计解释和可编辑产物。
- ReportAgent、PythonAgent、AuditAgent 的第一阶段输出都需要区分 `summary_for_chat` 与 `artifact_ref`。
- 前端不在第一阶段承担完整产物编辑器，但需要保证产物引用和继续操作入口稳定。

## 后续问题

- 轻量产物卡需要统一成一种通用组件，还是按 report/chart/audit 分类型组件。
- 第一阶段报告草稿卡展示几条摘要和哪些动作按钮。
- 图表第一阶段只展示图表建议，还是展示简单预览图。
- 审计解释卡对普通用户展示到什么深度，管理员视图是否从第一阶段就预留。
