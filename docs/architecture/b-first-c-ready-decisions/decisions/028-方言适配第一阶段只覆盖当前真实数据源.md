# 028 · 方言适配第一阶段只覆盖当前真实数据源

## 状态

- 状态：已敲定
- 时间：2026-06-26 16:17
- 触发：用户确认方言适配范围第一阶段只做当前真实数据源

## 决策

`sql_dialect_adapter.py` 第一阶段只覆盖当前 Datalogue 真实链路正在使用的数据源方言；不在 P0 同时实现 PostgreSQL / MySQL / SQLite 等多方言完整兼容。接口按可扩展方言注册表设计，但默认只启用当前真实数据源。

## 背景

第 023 和第 024 个决策已经确定：DSL / QueryGraph 到 SQL 的编译和方言适配由 Tools 完成，并通过 `query_plan_compiler.py` / `sql_dialect_adapter.py` 外壳承载。现在需要确定第一阶段方言适配范围。

## 选择理由

- P0 目标是跑通智能问数核心链路，不是建设完整跨数据库 SQL 编译器。
- 只覆盖当前真实数据源，可以把验收集中在真实页面、SSE、日志、Langfuse 和 artifact 一致性。
- 方言注册表保留扩展口，后续接新数据源时再逐个启用和验证。
- 未支持方言可以 fail closed，避免模型或工具猜 SQL 方言。

## 被排除方案

### 方案 A：第一阶段覆盖 PostgreSQL / MySQL / SQLite 三类基础方言

不采用。它扩展性更好，但会明显放大 P0 工作量和测试矩阵。

### 方案 B：不做方言层，继续由 SQL 生成处自行处理

不采用。它会让方言差异继续散落在旧链路里，不利于后续多数据源和 AgentScope adapter 复用。

### 方案 C：方言注册表预留，第一阶段只启用当前真实数据源

采用。接口 C-ready，执行范围 P0 可控。

## 对架构的影响

- `sql_dialect_adapter.py` 需要有明确的 `supported_dialects` 或等价注册表。
- 当前真实数据源方言为第一阶段唯一启用方言。
- 未支持方言必须 fail closed，返回明确错误摘要和 trace-only 诊断。
- LLM 不参与方言猜测。

## 对开发计划的影响

- P0.3 的 dialect adapter 验收范围收窄为当前真实数据源。
- 测试需要覆盖当前真实数据源成功和未知方言 fail closed。
- P2 / 后续计划中再补多方言扩展目标。

## 后续问题

- 当前真实数据源类型需要在实施前从 datasource 配置中确认，并写入 adapter 的初始注册表。
- 新数据源接入时是否要求同时补 dialect adapter contract test？
- 多方言支持进入 M4 还是 AgentScope runtime 前置目标？
