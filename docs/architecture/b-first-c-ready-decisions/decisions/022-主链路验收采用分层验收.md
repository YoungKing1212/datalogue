# 022 · 主链路验收采用分层验收

## 状态

- 状态：已敲定
- 时间：2026-06-26 12:55
- 触发：用户确认采用方案 3

## 决策

第一阶段真实链路验收采用分层验收。P0 智能问数主链路用例强制“五件套一致”；普通 UI、动作禁用态和增强能力预留项采用轻量验收，不要求每个预留入口都跑完整 Agent 链路。

## 背景

本轮头脑风暴已经把第一阶段目标收敛为先跑通智能问数核心链路，并将 ReportAgent、导出、完整工作台、多产物编辑、完整 DAG retry 等能力后置。最后需要确定验收口径，避免后续开发计划既过松导致链路假通，又过严导致预留能力验收成本过高。

## 选择理由

- P0 主链路必须严，符合数语一贯的真实链路验收要求。
- 预留动作和增强能力不应被要求跑完整 Agent 链路，否则会拖慢第一阶段。
- 分层验收能把“核心链路是否真的打通”和“协议预留是否正确”分开判断。
- 该口径方便后续制定开发计划时分配测试成本和验收证据。

## 被排除方案

- 只验收前端页面和最终 answer：速度最快，但容易漏掉 SSE、artifact、trace、状态写入和前端展示不一致的问题。
- 所有功能都强制五件套一致：最严谨，但对禁用态、预留入口和增强能力成本过高。

## 对架构的影响

验收分层如下：

```text
P0 主链路：
  - 真实页面展示
  - SSE event envelope
  - 后端日志
  - Langfuse trace
  - query_artifact / conversation_state

普通 UI / 动作禁用态：
  - 页面展示
  - event envelope
  - disabled_reason / action payload

增强能力预留项：
  - 协议存在
  - 禁用态正确
  - 不触发后端增强链路
```

P0 主链路至少覆盖：用户提问、能力路由、候选数据集确认、受控查询执行、最终 answer、`artifact_card`、`primary_ref` / `related_refs`、事件 envelope、状态写入和历史回放。

## 对开发计划的影响

- P2 需要把真实链路验收用例拆成 P0 五件套验收和轻量协议验收两类。
- P3 的 Chat 入口、`ask_bi`、`ArtifactCard`、`retry`、事件 envelope 和引用写入必须进入 P0 主链路验收。
- `export`、`continue_edit`、ReportAgent、完整工作台、多产物编辑等预留能力第一阶段只验协议、禁用态和不触发增强链路。
- 后续开发计划需要为每个 P0 用例写清楚验收证据来源和失败定位顺序。
